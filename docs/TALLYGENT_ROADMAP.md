# Tallygent — 产品决策与渐进式建设路线

决策日期：2026-10-24（Asia/Shanghai）。

## 1. 已确认的名称与本次边界

- 正式产品名：**Tallygent**，大写 T；不再把 Codex 当作产品品牌，Codex / Claude Code 是被监测的服务名。
- 用户提供的四阶段保留：Monitor → Insights → Planner → Control。
- 当前已验收的运行基线是 v0.5.9 / build 45；v0.6.0 / build 46 是首个 Tallygent 本地测试候选。
- 品牌迁移不改变 Bundle ID、用户设置和数据；是否公开发布仍需单独确认。
- 后续采用增量建设，不重写已工作的原生面板，不恢复 WidgetKit，不把粒子实验混入稳定版。
- 2026-10-25：按用户优先级先推进 build 47 的 [Planner 3.0/3.1 与 3.2 基础](PLANNER.md)，不代表 Monitor 连续观测库或 Insights 已完成，也不启用 3.3 自动路由。

建议定位：**本地优先的 Agent 额度与工作安排助手：知道还剩多少，也知道下一步如何安排。**

## 2. 现有基础与真实缺口

| 领域 | 已有实现 | 下一步缺口 |
| --- | --- | --- |
| 展示 | 三种原生可移动面板、单面板所有权、玻璃设置、秒级系统时钟 | 保持稳定；不要在小面板塞入完整计划工具 |
| Codex | 主 App 管理 app-server；额度、重置、七日 Token 图与刷新门禁 | 有效采集事件的连续历史，不只是最新缓存和日汇总 |
| Claude | statusLine 规范化桥接、单会话绑定、独立缓存、缺失/到期语义 | 真实订阅验收；桥接输入级历史；不可宣称后台主动查询 |
| 协调 | `QuotaMonitor` 负责服务选择，迟到响应不覆盖其他服务 | “启用采集”与“当前展示”分开；当前 Codex 首次连接仍取决于选择 |
| 模型 | `AgentService`、`UsageWindow`、`UsageSnapshot` 已存在 | 补来源/可信度/能力与周期标识；历史不能直接序列化含邮箱和玻璃设置的整份 UI 快照 |
| 质量 | 三系统完整 Xcode、双架构、签名、最终 DMG 门禁与真人桌面验收 | 新增改名升级、历史/规则/权限回归；既有门禁全部保留 |

已有七日 Token 日汇总**不能反推出过去每一刻的订阅额度**，历史从启用新采集后积累，不补造过去的数据。

## 3. 对创新点的校准

2026-10-24 只读核对的原始项目资料（不是完整市场调查，也不是运行验收）：

- [CodexBar](https://github.com/steipete/CodexBar)：多服务额度、重置、成本/状态、提醒等。多服务数量本身不构成差异化。
- [Codex Claude Usage Monitor](https://github.com/johnrizzetto/codex-claude-usage-monitor)：已有理想节奏比较、每小时可用额度和耗尽时间估计。预测耗尽时间本身也不是空白。
- [ccusage](https://github.com/ccusage/ccusage)：已有本地 Token、成本、日期/会话/项目统计。历史图表属于基础能力。
- [ccx](https://github.com/aaronwong1999/ccx)：已有 Claude/Codex 上下文交接。跨 Agent 切换本身不能宣称独创。

**优先验证的差异化假设**：把“可信额度观测 → 多窗口约束 → 用户任务队列 → 可解释安排建议 → 实际结果反馈”形成闭环，而且不要求用户授予执行权限。

示例是回答“现在先做哪个任务、留多少额度、什么时候再开大任务、为什么建议等待”，不是保证任务一定完成或自动花完订阅。桌面玻璃面板是持续可见的入口，Planner 才是值得验证的产品价值。该组合是否足够差异化，需要真实用户对照验证，不能仅凭未搜索到同名项目判断。

## 4. Phase 0 — 安全品牌迁移（前置工程工作）

此阶段不增加新的产品大功能，只完成 Tallygent 的安全升级路径。

- 更改 App 显示名、菜单品牌、DMG 展示名、图标说明和文档；服务卡片仍使用各服务自己的名称/标识。
- 保留 `dev.codexquota.app` bundle ID、UserDefaults 键、`desktop-glass-panel` 窗口保存标识、现有数据目录和桥接 CLI 参数。内部历史名字不是必须重构的缺陷。
- 工程/target/scheme 名可先保留，避免为品牌迁移增加无收益的工程改动。
- 当实际 `.app` / 可执行文件路径变更时，必须同步更新打包脚本、门禁路径和安装说明；检查产物名称应从实际 bundle 元数据取得，不能一半旧名、一半新名。
- **Claude 迁移风险**：`ClaudeBridgeSetup` 的 statusLine 保存的是绝对可执行文件路径，且会拒绝路径变更。需要显式的重新接入引导；仅在现有命令确实由本 App 管理时恢复/重装，保留原始备份，不静默覆盖第三方配置。不能只改文件名就宣布完成。
- 验证旧版与新版同时存在时不会双进程争抢数据；旧副本保留可恢复备份，但不留两个活跃安装。不要为改名清空账户数据或系统缓存。
- 不改写已验收 build 45 或其不可变标签；新二进制使用更高 build，再完整走门禁。

验收：从现有安装升级后，参数/位置/数据仍在；重新启动及旧版回退正常；新名包通过完整门禁；已启用、未启用、第三方 statusLine 三种升级路径都可说明且可恢复。

## 5. Phase 1 — Tallygent Monitor：先拥有可信的观测基础

### 1A. 增量统一数据契约

复用当前模型与两条来源，不先搭插件框架、云服务或通用 RPC 总线。只有当来源确实存在不同能力时，增加小型能力描述：额度窗口、重置字段、Token 历史、主动刷新/被动事件等。

最小历史样本包含：

- schemaVersion / observationID；provider；account/context scope（未知允许为空）；session 标识（会话不等同账户）。
- window kind / provider 原始窗口标识 / duration / usedPercent / resetsAt。
- source kind；本地 receivedAt；providerUpdatedAt（仅来源确实提供时填写）；validity / unavailable reason。
- 明确可选的 quota-pool 标识；无法确认共享池时不能把多个来源额度相加。

严格区分“系统时钟”“最后收到数据”“来源实际更新时间”。秒级时钟变化不是数据刷新；再次读缓存也不产生新采集记录。订阅百分比、Token 数、API 费用分开存储和展示，不互相伪换算。

### 1B. 连续记录有效输入，而不是重复保存界面

- 在 Codex 有效来源响应入口记录观测；成功响应即使数值未变也可证明一次真实观测，区别于 UI 重绘。
- Claude 必须在桥接接受有效输入时追加记录：仅靠 GUI 每两秒读取被覆盖的最新文件，会漏掉中间事件，也会把旧缓存误当新样本。
- 使用系统 SQLite 作为小型本地观测库，事务、版本迁移与有界锁等待即可；不引入 ORM/新后台守护进程。两进程写入路径必须验证并发和中断恢复。
- 保留旧缓存读取兼容，迁移期间明确最新记录与历史的单一写入规则，避免双写中断后互相覆盖。
- 存规范化数值和必要上下文，不存提示词、对话、源码、邮箱、token 或完整设置 JSON。默认保留期建议 30 天，提供明确清理/导出；权限限制不等于数据库已加密。
- 无效输入只记录有限诊断原因，不写原始敏感载荷；事件 ID、时间和来源用于防止重放。不能简单把所有相同百分比的真实新观测删掉。

### 1C. 采集独立于当前显示

主 App 仍是连接所有者。“哪些来源已启用”独立于“当前卡片显示哪个来源”；切面板不启动第二个连接，也不关闭仍被启用的采集。Claude 仍依赖用户启用的会话桥接，无法承诺持续后台读取订阅服务器。

验收：重启/睡眠恢复、跨日/时区、损坏记录、并发输入、重复缓存读取、来源切换、会话变化、重置点、旧版升级均有回归；历史不混服务、不混已知账户，不伪造缺失数据。Claude 无真实账户时可继续 Codex 历史开发，但始终保留实验性标签。

## 6. Phase 2 — Tallygent Insights：解释用量，不制造确定性

第一批：周期历史、使用节奏、多来源重置时间轴、可关闭且去重的低额度/重置提醒。新图表主要进入 App 详情，桌面面板仍以额度为主。

- 节奏基线只有在窗口类型、持续时间与重置语义已知时可算；滚动窗口不能盲目当成固定周期。
- 速度使用同一来源/上下文/同一额度窗口内的有效观测。跨重置、负跳变、身份切换、睡眠大间隔和过期来源先分段，不计算成负消耗或瞬间补满。
- 简单耗尽估算可用 `剩余额度 / 近期消耗速度`，但必须显示适用假设和范围；无有效正向变化、历史不足或数据陈旧时显示“暂无法估计”。不以零速度推断永远够用。
- 额度是整数百分比，存在分辨率限制；未来任务负载变化和其他设备用量也会使预测失效。先透明规则，不先训练 AI 模型；没有回测证据不显示虚构的置信概率。
- 5h 和周额度都是约束，不能只看更宽松的那一个。多来源时间轴分别显示，不合计成一个“总余额”。未来重置表示预计时间，不保证账户届时获得固定可用容量。

验收：使用历史回放比较估计与后续观测，记录误差和不可估计率；与简单基线对照，规则未校准前标明估计性质。提醒不得因反复刷新、窗口切换或休眠唤醒而连发。

## 7. Phase 3 — Tallygent Planner：Smart Runway 是优先产品假设

### 3A. 无执行权限的任务安排

用户手动加入任务，标记小/中/大、优先级、可选截止时间、可接受的 Agent 和依赖。先做本地列表和建议，不读取项目正文、不启动 Agent、不改提示词。

输出“建议先做 / 建议等待 / 保留额度 / 信息不足”，并列出依据：有效观测时间、当前约束窗口、近期趋势、下一重置、用户的保留量、任务的兼容来源。

冷启动时小/中/大只是相对规模，不能硬编码“小任务=5%”。没有任务成本样本时只给压力与时间安排提示，不输出“保证能完成 N 个任务”。可以接受用户手填预算，但必须标成用户估计。

### 3B. 用完成反馈改善，而非伪造任务归因

- 用户手动开始/完成，保存最小本地结果与可选满意度。
- 开始/结束间的账户额度变化不是天然的任务成本：存在其他设备、并发会话、延迟上报与周期重置。无法隔离的样本标记“期间账户变化”，排除精确成本学习。
- 只有足够可比的同来源/窗口/任务类别样本，才给成本范围；样本量、观测质量和估计依据可见。跨服务百分比不能直接比较效率，不能只按剩余百分比推荐 Agent。
- 保留用户覆盖建议的权利。模型能力匹配最初由用户选择，不能假装软件知道哪一个 Agent 一定更适合任务。

Smart Runway 的目标是“在多个额度约束下，为任务队列提供有解释的可行性范围”，不是保证剩余 Token、工时或任务完成数。

验收：邀请真实使用者比较“只看百分比”和“看安排建议”是否改善选择、减少意外中断；同时记录错误建议/不确定输出。先证实建议有用，再增加复杂预测。用户数据收集与导出必须自愿，不默认上传遥测。

## 8. Phase 4 — Tallygent Control：先关注事件，后考虑执行

拆成两个可独立交付的子阶段：

1. **Attention Inbox（只读）**：用户选择来源的原生事件/Hooks，展示等待审批、完成、失败等需要关注的事项。事件丢失时显示未知，不能靠额度不变猜测任务卡住；没有官方/可验证能力的来源不支持该项。监测模式用户不应被迫开放新权限。
2. **可选控制**：只有在来源提供可靠接口、用户明确授权后，才逐项支持启动、暂停/恢复、交接。权限按 Agent/项目/动作限定，保留确认、审计和撤销；预览跨 Agent 传输的内容。不能用强制杀进程冒充安全暂停，也不默认转发项目或对话。

已有交接项目可以研究其交互，但不直接运行安装脚本或照搬其权限模型。跨 Agent 任务、身份、上下文格式和恢复语义不一致，应按具体组合验收，不承诺通用无损迁移。

进入条件：Phase 3 确有用户价值且用户有控制需求；每个来源具备受支持接口、安全边界和真实测试者。无需为了四阶段齐全而强行实现。

## 9. 建设顺序与发布边界

推荐小步顺序：**品牌迁移测试包 → Monitor 契约/历史测试包 → Insights → Planner 小范围验证 → 按需 Control**。不要在一个版本里同时改品牌、数据模型、绘制和执行权限。

- 第一批先做 Phase 0 + Phase 1 的工程切分，复用 `QuotaMonitor`、当前来源与原生面板；不先增加第三个 Provider。
- 第三个来源先通过数据接口/认证/字段/真实账户可测试性评审，再写适配；不是把枚举加一项就算支持。
- 没有 Claude 订阅仍可做品牌、规范化存储、Codex 历史和规则测试；不能因此宣布 Claude 真机接入验证通过。
- 现有发布门禁不降级：完整 Xcode、双架构、最终签名载荷、三系统、渲染/同步/单面板及桌面真人验收。全运行门禁仅在隔离 CI 用户执行。
- 新增最小回归分别保护：品牌升级兼容、逐来源采集、历史事件去重/保真、周期分段、冷启动预测、通知去重、可选执行权限。
- 不承诺未公证的安装包无需系统安全确认；Developer ID/公证与产品创新是独立交付事项。
