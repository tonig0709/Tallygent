# 原生窗口布局约束 — build 49

## 本次根因

本机 build 47 主窗口约为 900 × 652pt，已经高于 760 × 620pt 内容最小值。截图中的竖排残字不是旧小组件缓存，也不是窗口默认尺寸不足。

旧写法把 `Picker("监测服务")` 的隐式原生标题与分段选项一起放进固定 320pt。选项的原生最小宽度先占满空间，中文标题被压成极窄的多行文本。外层窗口 `fittingSize` 和预览页宽度仍然正常，所以原来的门禁没有发现内部文字损坏。

工作区 340pt、Planner 来源 180pt，以及侧栏内的带标题分段控件具有相同风险。长账户或错误信息与所有动作挤在一行，也会竞争宽度。

## 持久约束

1. 标题与控件分别负责自己的布局。有限空间内使用 `AdaptivePicker`：外置标题保持完整单行，原生 Picker 的隐式标题隐藏，同时保留辅助功能名称。
2. 分段选项按固有尺寸判断，放不下就改用原生下拉选择；不把中文压成竖排，不以缩小字号掩盖问题。动态模型目录直接使用下拉，不创建大量分段按钮。
3. 工作区和详情页头按内容选择横排/竖排；宣传语不能挤占导航。状态信息独占一行并允许自然换行，动作放不下时改为竖排。
4. 玻璃设置的标题置于控件上方；主窗口、侧栏和设置弹窗共用同一选择器规则。
5. 桌面面板的 164/344/680pt 原生尺寸与玻璃渲染不是错误的固定宽度，保持不变。也不修改源数据、采集频率、Planner 规则或存储。

## 自动回归

`scripts/release-preflight.sh` 必须继续运行 `scripts/check-desktop-panel.sh`。后者仅可在隔离 CI 用户执行，不能为修布局而清理用户设置或启动模拟账户服务。

- 测量实际语义文字的 frame、同字体理想尺寸与所属区域边界，不再只判断整窗大小。
- 中文/英文环境、深浅色、13/21pt 基础字体；覆盖 760、900、1030、1079、1080、1120、1400pt，特别包含用户实际宽度和侧栏临界点。
- 在同一个原生窗口内缩小、跨越分栏断点、再恢复，避免只测试新建窗口的理想状态。
- 使用合成长账户、错误状态和展开的 Planner 字段，防止空状态掩盖文字冲突。
- 保留真实的错误负对照：窄行里的中文标题与原生分段控件发生竞争时，同一套几何断言必须拒绝它。若负对照也能通过，门禁本身失败。
- 测量副本仅在隔离测试中启用，正常 App 不创建隐藏的测量控件。保留原有非黑屏、同步、单面板、鼠标路由、签名、双架构和 DMG 检查。

测试矩阵能防止已知约束回归，但不能保证未来所有 macOS、字体或语言变化绝不影响布局。新增控件、语言和系统支持时，应将相应极端状态加入同一门禁，而不是继续加大窗口默认值。

## 多语言下的原生尺寸测量 — build 54

三种语言必须在独立原生 bundle 进程中实际加载 `en`、`zh-Hans`、`zh-Hant` 资源；仅更改 SwiftUI 的 `locale` 环境不能证明动态 `String` 已翻译。

English 展开 Planner 在 760pt／21pt 字体下暴露了一个门禁误判：`NSHostingView.fittingSize` 给出无约束的理想宽度（980pt 内容上限加 15／17pt 滚动条），并非当前视口中的最小必需宽度。实际内容为 743／745pt，语义标签与容器均在视口内。不能通过缩短正常翻译、放大最小窗口或删除几何检查来掩盖这种差异。

展开 Planner 现在使用 `NSHostingController.sizeThatFits(in:)` 测量给定视口下的尺寸，原来的 `fittingSize` 保留为诊断。内容和页头容器也必须被测量；所有标题的理想文字尺寸、控件边界、原生窗口尺寸、同窗缩小恢复与主题／大字体矩阵保持有效。

同一套给定视口测量必须拒绝“固定 900pt 内容放入 760pt 视口”的负对照；原有压缩中文标题的真实原生 Picker 负对照继续保留。这同时防止无约束理想宽度造成误报，以及真正的最小宽度外溢被放过。
